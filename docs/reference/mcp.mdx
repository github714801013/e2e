`e2e mcp` lets coding agents such as Claude Code and Cursor inspect your app,
try locators, and take masked screenshots before writing tests. It runs over
stdio and uses the project's configured engine. `--http` serves the same app
tools plus the [script tools](#script-tools) and [job tools](#job-tools) over
Streamable HTTP, one MCP session per authenticated client. For setup and what
to ask the agent, see the [MCP server guide](/mcp-server).

```json title=".mcp.json"
{
  "mcpServers": {
    "e2e": { "command": "npx", "args": ["e2e", "mcp"] }
  }
}
```

Four MCP tools manage the session and call its available app tools. The app
tool catalog reloads from the config whenever a session opens.

## Reference

### Flags

<CodeGroup>
```bash npm
npx e2e mcp [--config <path>] [--target <name>] [--headed] [--max-sessions <n>] [--max-sessions-per-domain <n>]
```

```bash pnpm
pnpm exec e2e mcp [--config <path>] [--target <name>] [--headed] [--max-sessions <n>] [--max-sessions-per-domain <n>]
```

```bash bun
bunx e2e mcp [--config <path>] [--target <name>] [--headed] [--max-sessions <n>] [--max-sessions-per-domain <n>]
```
</CodeGroup>

| Flag | Default |
| --- | --- |
| [`--config <path>`](#config) | discovered like `e2e run` |
| [`--target <name>`](#target) | the only target |
| [`--headed`](#headed) | headless |
| [`--max-sessions <n>`](#max-sessions) | `4` (stdio) |
| [`--max-sessions-per-domain <n>`](#max-sessions-per-domain) | `20` (HTTP) |
| [`--http`](#http-mode) | stdio |
| [`--host <host>`](#http-mode) | `127.0.0.1` |
| [`--port <port>`](#http-mode) | `3001` |
| [`--path <path>`](#http-mode) | `/mcp/e2e` |
| [`--allow-host <host>`](#http-mode) | the loopback names for the bound port |
| [`--allow-origin <origin>`](#http-mode) | the loopback origins for the bound port |
| [`--trusted-proxy <address>`](#http-mode) | none |
| [`--session-ttl <seconds>`](#http-mode) | `600` |
| [`--max-body <bytes>`](#http-mode) | `4194304` |
| [`--max-workers <n>`](#job-tools) | `4` |
| [`--max-runs <n>`](#job-tools) | `2` |
| [`--test-root <path>`](#script-tools) | the working directory |

#### `--config`

The config every session loads unless `open_session` names one. Each
session loads it afresh ([Several sessions](#several-sessions)).

#### `--target`

The target a session opens on when `open_session` names none.

- Without it and without a name, the only target is used.
- Several targets and no name is `TARGET_REQUIRED`.

#### `--headed`

Shows the browser or simulator, when the engine supports it, in every
session whose `open_session` does not set `headed`.

- Sessions are headless by default, as in `e2e run`.

#### `--max-sessions`

How many native sessions may be open at once over stdio, 1 through 16. Each
session is its own browser or device. See
[Several sessions](#several-sessions).

```bash
e2e mcp --max-sessions 8 # default: 4
```

The flag does not apply with `--http`, which has no global session limit;
passing both is refused at startup. Use
[`--max-sessions-per-domain`](#max-sessions-per-domain) there instead.

#### `--max-sessions-per-domain`

With `--http`: how many sessions one principal may hold on one target domain,
1 through 100, shared by every token of that principal. A session counts from
a successful `open_session` until it closes that session or the session ends.
Opening another target past the limit reclaims the group's least recently
active session: its HTTP session is closed and the new one proceeds. A target
without an app URL, such as a device target, is keyed by its target name.

```bash
e2e mcp --http --max-sessions-per-domain 20 # default: 20
```

### Tools

| Tool | Description |
| --- | --- |
| [`open_session`](#open_session) | Opens a session |
| [`tools`](#tools-2) | Lists the catalog or one tool |
| [`call`](#call) | Runs one catalog tool |
| [`close_session`](#close_session) | Ends the session and its engine |

`session` may be left out while exactly one session is open. See
[Several sessions](#several-sessions).

#### `open_session`

Loads the config, starts the target's app command, boots the engine, starts
one attempt, and opens the app: its URL when the engine can navigate, or on a
device the [pinned app](/mobile#point-at-your-app), launched fresh. It installs
no build, so a local device target needs `app.bundleId`. Returns the session
id, the catalog, and the first observation. Its structured content names the
`target`, its `platform`, and its `appUrl` (absent for a device target).

```txt
open_session {target: "web", headed: true}
```

| Input | Type | Required | Does |
| --- | --- | --- | --- |
| `target` | string | no | The target to open. Otherwise `--target`, else the only target. |
| `config` | string (path) | no | The config for this session. Otherwise `--config`, else discovered like `e2e run`. |
| `headed` | boolean | no | `true` shows this session's browser or simulator, `false` hides it. Without it the session follows `--headed`. |

#### `tools`

Returns the catalog, one line per tool.

```txt
tools {tool: "locate"}
```

| Input | Type | Required | Does |
| --- | --- | --- | --- |
| `tool` | string | no | A catalog tool. Returns its full description and argument schema. |
| `session` | string | while several are open | The session id. |

#### `call`

Runs one catalog tool.

```txt
call {tool: "tap", args: {target: "n42"}, session: "<id>"}
```

| Input | Type | Required | Does |
| --- | --- | --- | --- |
| `tool` | string | yes | A catalog tool name. |
| `args` | object | no | The tool's arguments. |
| `session` | string | while several are open | The session id. |

- Arguments are validated against the tool's closed schema first. A wrong
  type or an argument the tool does not declare is `INVALID_ARGUMENT`, and
  nothing runs.
- An action that fails is an error result that still carries the screen it
  re-observed. It leads with the tool, its target, and the code:
  `navigate file:///etc/passwd failed: POLICY_DENIED: forbidden URL scheme: file:`.
- Project tools honor their AI SDK `toModelOutput` renderer, including when
  `execute` returns a string. Rendered `error-text` and `error-json` outputs
  are MCP error results (`isError: true`). The coding agent can tell a failed
  tool call from a successful one.

#### `close_session`

Saves a recording still running, ends the attempt, and disposes the engine.
It stops the app processes the session started once no other session uses
them.

```txt
close_session {session: "<id>"}
```

| Input | Type | Required | Does |
| --- | --- | --- | --- |
| `session` | string | while several are open | The session id. |

### The catalog

What `call` can run depends on the session's target.

| Catalog tool | Description |
| --- | --- |
| [`observe`](#observe) | Returns a fresh observation |
| [Actions](#actions) | Act on an observed node |
| [`dismiss_keyboard`](#dismiss_keyboard) | Hides the on-screen keyboard |
| [`locate`](#locate) | Tries a semantic locator |
| [`screenshot`](#screenshot) | Returns the masked viewport |
| [Point tools](#point-tools) | Act at a screenshot point |
| [`start_recording`, `stop_recording`](#recording) | Records a video of the app |
| [Project tools](#project-tools) | Your `defineTool` tools |

#### `observe`

A fresh observation, one node per line as `#id role "name" ...`, with the
current path and revision. Takes no arguments.

- A link's `href` is its path when it is on the app URL's origin, else
  origin and path.
- `mailto:`, `tel:`, and `blob:` targets keep their scheme.
- `…` marks what is left out: `?…` a query, `#…` a fragment, `data:…` or
  `javascript:…` an inline payload, a trailing `…` a target cut at 256
  characters.

#### Actions

`tap`, `double_tap`, `long_press`, `right_click`, `hover`, `type`, `press`,
`select`, `check`, `scroll`, `scroll_to`, `drag`, `upload`, `navigate`,
`back`, `type_secret`. Each returns the action's summary and what changed on
screen.

| Input | Does |
| --- | --- |
| A node id | From the newest observation. |
| The value, key, `checked` state, direction, drop target, project-relative `files`, URL, or secret name | What the verb needs. |
| `modifiers` (optional) | On `tap`, `double_tap`, and `right_click`, when the engine declares `tapModifiers`: a list of `Shift`, `Control`, `Alt`, `Meta`, `ControlOrMeta`, held for the click. |

- A verb the engine does not declare is not in the catalog.
- `upload` refuses a path outside the project, a hidden file, or a file
  under a hidden directory with `POLICY_DENIED`.
- `type_secret` is listed when the config declares `credentials` or
  `secrets` and the engine declares the `fill` action. The plaintext never reaches the agent.

#### `dismiss_keyboard`

Hides the on-screen keyboard. Takes no arguments. Listed when the engine's
keyboard declares `dismiss`, as the device engines do.

#### `locate`

Returns how many nodes match a semantic locator, which ones, and the
`screen.*` call to write.

| Input | Does |
| --- | --- |
| `role` (with optional `name`), `text`, `label`, `placeholder`, `testId` | Exactly one of them. |
| `exact` | Exact matching; `false` for substring, case-insensitive. |

- Zero or several matches name the error a test would get.
- A `name` matches the accessible name only. `observe` shows a `status`,
  `alert`, or `listitem` by its text, so one of those with a name that
  matches nothing also points at `getByRole(role).filter({ hasText })` and
  `getByText`.
- What it shows of a node passes the secret ledger, as `observe` does: a
  filled secret reads `<secret:name>`.

#### `screenshot`

The masked viewport as an image. Takes no arguments.

- From then on every action result carries a fresh screenshot.
- After a secret fill it answers `PIXEL_TAINTED`. See [Sessions](#sessions).

#### Point tools

Each takes `x` and `y` in the latest screenshot's pixels.

| Tool | Inputs | Does | Listed when the engine declares |
| --- | --- | --- | --- |
| `tap_at` | `x`, `y` | Taps a listed control under the point by id, otherwise the bare point through the engine's `performAt`. Without `performAt` the point must land on a listed control. | `tap` or `performAt` |
| `hover_at` | `x`, `y` | Hovers the same way: a listed control under it by id, otherwise the bare point through `performAt`'s `hover` kind. | the `hover` action or pointer kind |
| `type_at` | `x`, `y`, `value`; `replace` on an engine with a keyboard | Fills a listed input under the point by id. With a keyboard, anything else is tapped to focus it and typed into, at the caret unless `replace` is set. Without one, a point on nothing listed fails. | `type` or a keyboard |
| `press_at` | `x`, `y`, `key` | Sends the key to a listed control under the point by id. With a keyboard, anything else is tapped to focus it and the key goes through the keyboard. | `press` or a keyboard |
| `select_at` | `x`, `y`, `value` (the option's visible label) | Picks the option in the listed select-like control under the point. Nothing listed there fails. | `select` |

<Note>
Before the session's first `screenshot`, each point tool answers with the
line that says to take one, at no cost. Like `screenshot`, they answer
`PIXEL_TAINTED` after a secret fill.
</Note>

#### Recording

`start_recording` and `stop_recording` record a video of the app. Both are
listed when the engine records video.

```txt
call {tool: "start_recording", args: {name: "checkout-flow"}}
call {tool: "stop_recording"}
```

| Tool | Input | Does |
| --- | --- | --- |
| `start_recording` | `name` (optional): up to 64 letters, digits, `-`, and `_`, starting with a letter or digit | One recording at a time. A second start reports the one running. |
| `stop_recording` | none | Saves the video and returns each file's absolute path, or the URL where a provider keeps it. |

- A session records video only between `start_recording` and
  `stop_recording`, as many times as needed. The configured
  [`video`](/reference/config#video) mode applies to runs, not sessions, and
  a session writes no [trace](/reference/config#trace).
- Each recording is saved to `<output>/videos/<session>/<n>[-<name>].webm`
  (`.mp4` on mobile, and [`output`](/reference/config#output) is `.e2e` by
  default), where `n` counts the session's recordings.
- A web recording that spans a restart or a state reset has one file per
  page, `-part2`, `-part3`, and so on, in play order.
- A browser or device provider that records the lease itself records the
  session instead. [Kernel](/integrations/kernel) downloads its replay, saved
  here as `<n>[-<name>].mp4` like any other file. A provider that keeps its
  recordings is listed by URL instead of a file.
- `close_session`, the idle timeout, and the session TTL save a recording
  still running, and the close result lists its files.

<Warning>
Recordings are not masked and are not withheld after a secret was filled:
they are files for a person to watch, and no tool returns their pixels. A
secret typed into a plain input while recording is readable in the video,
and a recording stopped after a secret was filled says so.
</Warning>

#### Project tools

Project tools in `agents.default.tools` follow in the catalog under their
own names, scoped to the target's platform. A mobile project that passes
`mobileTools(...)` also gets `open_app`, `swipe`, and `alert`.

| Throws | When |
| --- | --- |
| `INVALID_CONFIG` | A project tool named like a built-in, at config load. |
| `UNKNOWN_TOOL` | A name not in the catalog. The message lists the names. |

## Setup

The server ships with `e2e`. `e2e init` offers to register it in
`.mcp.json` (Claude Code) and `.cursor/mcp.json` (Cursor). By hand:

<CodeGroup>
```bash npm
claude mcp add --scope project e2e -- npx e2e mcp
```

```bash pnpm
claude mcp add --scope project e2e -- pnpm exec e2e mcp
```

```bash bun
claude mcp add --scope project e2e -- bunx e2e mcp
```
</CodeGroup>

For clients that use a `mcpServers` config, add the entry shown above.
Codex reads the project's `.codex/config.toml` once the project is trusted:

```toml title=".codex/config.toml"
[mcp_servers.e2e]
command = "npx"
args = ["e2e", "mcp"]
```

The server is also listed in the
[MCP Registry](https://registry.modelcontextprotocol.io) as
`io.github.tester-army/e2e`. A client that installs it from there runs the
listed release with `npx` and must start it in the project directory. The
project still needs e2e and its engine installed, since the config imports
them. A listed release on another version than the project's e2e can reject
config keys it does not know; the registration above always matches.

The server needs no model: a project without the optional `ai` package
opens sessions and drives the app with the deterministic tools.

Start the server in the project directory. Config discovery works like
`e2e run`. For another config, see [`--config`](#config) and
[`open_session`](#open_session).

## Output

- Operator output goes to stderr, prefixed `e2e mcp:`. Stdout carries only
  the protocol.
- What your code writes through `console`, `process.stdout`, or
  `process.stderr` (the config's top-level code, project tools) goes to
  stderr with secret values redacted.
- Output printed while a config loads appears once it has loaded. If the
  load fails, that output is withheld, since the config's secrets are
  unknown.
- An error nobody caught is logged redacted and shuts the server down.

<Note>
A child process that inherits the server's stdio writes past this.
</Note>

## Sessions

A session is one attempt on one target. A `call` before any session is open
fails with `NO_SESSION`.

A session closes:

- on `close_session`,
- after 30 idle minutes,
- after 4 hours,
- when the client disconnects,
- on SIGINT or SIGTERM.

The client disconnects when it closes the server's stdin or dies. Then every
session closes, the app commands the sessions started stop, and the server
exits.

Sessions enforce what tests enforce:

- Node ids are valid only against the newest observation.
- A secret fills only through `type_secret`. Once one has been filled,
  [`screenshot`](#screenshot) and the [point tools](#point-tools) stay in the
  catalog but answer `PIXEL_TAINTED` for the rest of the session.
- A secret whose name starts with `<target>.` belongs to that target. The
  session's opening text names the target it is on; a secret for another
  target is still listed but is not this session's.
- Once the config has loaded, its secret values are redacted from every text
  a tool returns, a node `locate` found, an action's result, an
  `open_session` or `close_session` failure, a cleanup line, and the server's
  own log lines.
- Nothing a session does is recorded as a test result or into the replay
  cache. Its artifacts land under
  `<output>/results/mcp/<target>-<attemptId>/`, its videos under
  `<output>/videos/`. A later `e2e run` clears `<output>/results`; the videos
  stay.
- A queued call cancelled by the client does not execute when its turn
  arrives.

## Several sessions

Several sessions can be open at once, each on its own attempt and its own
browser or device. Over stdio, `--max-sessions` bounds them. Over `--http`
there is no global limit: each principal gets `--max-sessions-per-domain`
sessions per target domain, where the domain is the target's app URL host (or
its target name for a target without one). Parallel agents, such as a
coding agent's subagents, share one server this way: each opens a session
and passes its id to every `tools`, `call`, and `close_session`.
[Bug bashes](/bug-bash) use this: every verifying subagent drives its own
session.

| Throws | When |
| --- | --- |
| `SESSION_REQUIRED` | A call without `session` while several are open. The message lists the open sessions. |
| `NO_SESSION` | A `session` id that is not open. For a session that is closing or ended, the message says why. |
| `SESSION_OPEN` | An `open_session` past the limit, or while the server shuts down. |
| `CONFIG_IN_USE` | An `open_session` on another config while sessions are open. |
| `ENGINE_IN_USE` | A second session on an engine created inside a package. |
| `CANCELLED` | An `open_session` the client cancelled or disconnected from, or the server shut down during, once what it started has stopped. |

- A session holds its slot from `open_session` until its attempt has closed,
  so sessions still booting or still closing count toward the limit.
- Sessions open at once share one config: credentials and secrets resolve
  through one registry per process.
- While the server shuts down it cancels sessions still opening and waits
  for them, closes every session, and refuses new ones. A cancelled open
  fails once what it started (an app command still waiting on its
  `readyUrl`, say) has stopped.
- Each session loads the config afresh, down to the files it imports by
  path, such as a base config it spreads, so each gets engine instances of
  its own. An engine created inside a package is one instance every session
  shares.
- Sessions on one app command share its process: the first session starts
  it, and it stops when the last of them closes. A URL declared with port
  `0` gets its own port in each session, and so its own process. A shared
  start that every waiting session gave up on is cancelled, and the next
  session starts it afresh.
- On mobile, each session needs its own simulator or emulator: declare one
  target per device, each naming its `device`, and open each session on its
  own target.

## HTTP mode

`--http` serves Streamable HTTP instead of stdio:

<CodeGroup>
```bash npm
E2E_HTTP_MCP_TOKENS='[{"token":"<at least 32 characters>","principal":"alice"}]' npx e2e mcp --http --port 3001
```

```bash pnpm
E2E_HTTP_MCP_TOKENS='[{"token":"<at least 32 characters>","principal":"alice"}]' pnpm exec e2e mcp --http --port 3001
```

```bash bun
E2E_HTTP_MCP_TOKENS='[{"token":"<at least 32 characters>","principal":"alice"}]' bunx e2e mcp --http --port 3001
```
</CodeGroup>

The endpoint is `http://127.0.0.1:3001/mcp/e2e`. `--port 0` asks the OS for a
free port, and the listening URL is printed to stderr.

### Tokens

`E2E_HTTP_MCP_TOKENS` is a JSON array; each entry is
`{ "token", "principal", "tools" }`.

| Field | Required | Does |
| --- | --- | --- |
| `token` | yes | The Bearer token, at least 32 characters. |
| `principal` | no | The session and job owner, `"default"` when absent. Required when `tools` includes a job tool, since jobs are private to their principal. A session id is usable only by the token that opened it. |
| `tools` | no | Which tools the token may call: `open_session`, `tools`, `call`, `close_session`, `list_test_scripts`, `get_test_script`, `save_test_script`, `run_test`, `get_test_status`, `get_test_report`. Absent means the four native tools plus `list_test_scripts` and `get_test_script`; saving a script and running jobs are granted only by naming them. |

Every request to the MCP endpoint needs `Authorization: Bearer <token>`. A
missing or unknown token is `401`, and it creates no session. Tokens are read
once at startup. They are not passed to the per-session child, which runs
project code.

### Script tools

Three tools let an HTTP client work on the project's test files. A token may
call them only when its `tools` lists them.

| Tool | Does |
| --- | --- |
| `list_test_scripts` | Collects the project and groups the tests by file, with paths relative to `--test-root`. Arguments: `prefix`, `keyword`, `limit`. |
| `get_test_script` | Returns one file's `path` and `content`. |
| `save_test_script` | Writes one file atomically. Arguments: `path`, `content`, `overwrite`. |

Every path resolves under `--test-root`, the working directory by default,
resolved once at startup; a root that is not a readable directory fails the
command before it listens. A path must name a `.e2e.ts` file. A path that
leaves the root is `POLICY_DENIED`. Links are resolved and the result must
stay under the root, and a path whose final component is a file symbolic link
is refused. An absolute path is compared as written, so pass the canonical
spelling of the root or a relative path. A save creates missing parent
directories under the root; a read whose parent is missing is
`SCRIPT_NOT_FOUND`.

- `list_test_scripts` collects through a child process, because collection
  executes each test file's top-level code. The child has a 30-second deadline
  and its output is drained but never returned. A failing import or collection
  error is `COLLECTION_ERROR`, naming the exit status only: the child's stderr
  belongs to project code, and a test or config that prints a secret would put
  it in the tool result. Run collection locally for the error text. The
  collection covers the whole project, as a run does; only files under
  `--test-root` are listed.
- `save_test_script` writes at most 256 KiB through a temporary file in the
  same directory and a rename, so a reader sees the old file or the new one,
  never half of one. It refuses an existing file unless `overwrite` is true
  (`SCRIPT_EXISTS`).
- Saves are serialized. A save that lands while
  `list_test_scripts` is collecting fails that call with `SCRIPT_CHANGED`;
  call `list_test_scripts` again, so a listing never reports a half-changed
  project.
- A token that grants only script tools never starts a native `e2e mcp` child
  and has no guide resources.

### Job tools

Three tools run test files asynchronously, so an agent can queue a batch and
keep working. A token may call them only when its `tools` lists them.

| Tool | Does |
| --- | --- |
| `run_test` | Queues one to fifty project-relative test files on one target and returns the job at once. Arguments: `targetId`, `testFiles`, `idempotencyKey`. |
| `get_test_status` | One job's `status`, `counts`, timestamps, and `error`. Argument: `jobId`. |
| `get_test_report` | The status plus per-test `results`: title, project-relative file, status, duration, attempts, bounded failure evidence, and artifact kinds. Argument: `jobId`. A result never carries an absolute path, though an `error.message` may quote one the Runner reported. |

`run_test` returns once the temporary Runner has started; collection and the
tests continue after the call. A job is `queued` while its record is written,
then `collecting`, `waiting_auth`, `running`, and finally one of `passed`,
`failed`, `timed_out`, `interrupted`, `infrastructure_error`, or `rejected`.
Submissions for one target join its current run; a run with no work seals after
two seconds, and the next submission starts a new one once the sealed child
has exited, so one target never runs two logins beside each other. Each run
executes its authentication setup once and every later job reuses that
snapshot. A repeated
file in the same run gets its own result: the Runner's `repeat` index makes the
two results distinct, so each job reports only its own. A run waits at most two
minutes for its authentication setup. One job has fifteen minutes from
`run_test`, collection included, and at most 1000 selected tests; a selection
over that is `rejected` with `INVALID_ARGUMENT`. A job that times out stops a
run it has to itself; one still draining ten seconds later is killed, so a
stuck test does not keep the slot. A timed-out job beside live neighbours
stops only itself, since killing the run would cut them too.

A run-level hook failure applies to every job the run completed: a failing
`afterAll`, for example, turns a job that already reported `passed` into
`failed` with `HOOK_FAILED`.

`--max-workers` (default 4, 1 to 64, `--http` only) caps how many workers one
run may start: a project whose `workers` is higher still starts no more than
the cap, while a lower project value stays lower. Workers start only for
queued work. `--max-runs` (default 2, 1 to 16, `--http` only) bounds runs alive
at once; a submission for another target past it is refused with
`CAPACITY_EXCEEDED` until one run ends. One run also holds at most 20 unfinished
jobs, refused the same way. A run has thirty minutes in total; jobs it still
holds at that point end `timed_out` with `RUN_TIMEOUT`.

The run, its authentication, and the two capacity limits are shared by every
job on one target, whichever principal submitted it. A principal only decides
who may read a job, not what it executes beside: a job that times out during
collection stops the shared run, so its neighbours end `rejected`,
`interrupted`, or `infrastructure_error` rather than waiting for a collection
that will never resume.

Jobs are addressable by `jobId` across sessions and connections, so a client
that disconnects can reconnect with the same token and keep polling. A job
belongs to the principal that submitted it: another principal gets
`POLICY_DENIED`, and an unknown id is `INVALID_ARGUMENT`. For one principal,
the same `idempotencyKey` with the same target and files returns the original
job; the same key with a different request is `INVALID_ARGUMENT`.

A job record is written to `.e2e/http-jobs/<jobId>.json` before the Runner
hears about it, and each run writes under `.e2e/http-jobs/runs/<random-id>/`
(not the `runId`), which the gateway removes when that run stops. Run one gateway per project: two would
share those directories and race over the same job records. On POSIX the
record is mode `0600`; Windows applies the project directory's ACL instead. A
link in that path fails the gateway at startup rather than writing outside the
project. The gateway loads the records at startup and marks one a previous
gateway left unfinished as `interrupted`; a job whose Runner exited without
reporting an outcome ends `infrastructure_error` with `WORKER_EXIT`. Nothing is
replayed: a test with side effects never runs twice because its status was
lost. A finished record stays readable for 14 days and is then removed, its
idempotency key with it. A report carries at most 50 results and 256 KiB.

On SIGINT or SIGTERM the gateway seals every run, waits for its child within
the stop grace, then kills what is left; the jobs it cut end `interrupted`,
including a submission the child had not accepted yet. Each run's
authentication snapshot lives under its own run directory and is never reused
by a later run.

A token that grants only job tools never starts a native `e2e mcp` child and
has no guide resources.

### Security

- Host and Origin are checked before the token. The defaults accept only
  `127.0.0.1`, `localhost`, and `::1` with the bound port; there is no
  wildcard. An absent Origin is allowed, since non-browser clients send none.
  `--allow-host` and `--allow-origin` replace the defaults; an Origin of
  `null` or a malformed one is refused.
- `--trusted-proxy` names a proxy address whose `X-Forwarded-For` is believed
  for the log line. It changes nothing about authentication: the Bearer token
  is always the identity.
- A session id bound to another token is `403` and an unknown id is `404`.
  There is no global session cap: each target a session opens joins its
  principal's quota for that target domain
  ([`--max-sessions-per-domain`](#max-sessions-per-domain)). A session that
  closes keeps its slot until its child exits; a reclaimed session frees it
  for the session that triggered the reclaim.
- `--max-body` bounds the request body. A larger one is `413`.
- Each MCP session gets its own `e2e mcp` child, spawned on the first native
  tool or resource call and reused for the rest of the session. A session that
  never calls one spawns no child, and a token with no native tool never does.
  The child is limited to one native session, so a client cannot open a second
  browser in one HTTP session.
- The script tools are confined to `--test-root`. They never follow a link out
  of it, never create directories, and never write a path that is not a
  `.e2e.ts` file. Their collection child runs with the gateway's environment,
  minus `E2E_HTTP_MCP_TOKENS`.
- A job belongs to its HTTP principal, not to code running in the project. The
  Runner child executes the project's test and config code with the runner's
  full authority: that code can read `.e2e/http-jobs` and forge messages on the
  job channel, and on the same user it can read the gateway's environment
  (`/proc/<pid>/environ`) and so every token. `principal` and `tools` separate
  clients functionally, not the project from its own gateway: clients that do
  not trust each other need their own user, project, and gateway.
- `/healthz` is the gateway's own route, so `--path /healthz` is refused at
  startup.
- A session closes when the client sends `DELETE`, when `--session-ttl` runs
  out with no request or open stream, when its child exits, or on shutdown.
  `--session-ttl 0` disables the idle timeout. A client that only closes its
  socket leaves the session to the TTL, because HTTP keeps no connection to
  watch.
- Nothing here terminates TLS. Run it behind a TLS proxy when clients are not
  on the same machine, and add that proxy's Host and Origin values.

### Health

`GET /healthz` answers `{"status":"ok","version","sessions","uptimeMs"}`
without a token and without session details. It shares the Host and Origin
checks.

### Responses

| Status | When |
| --- | --- |
| `401` | Missing or unknown Bearer token. |
| `403` | Refused Host or Origin, or a session id owned by another token (or another principal). |
| `404` | Unknown path or session id. |
| `413` | Request body over `--max-body`. |

## Exit codes

| Code | When |
| --- | --- |
| `0` | The client disconnects, with or without a session open, or a signal ends it. |
| `1` | An uncaught error shuts the server down. |
| `2` | The command line is invalid. |
| The error's [category code](/reference/cli#exit-codes) | A startup failure. |

Config and engine failures come back as tool errors with the same codes the
CLI prints.
