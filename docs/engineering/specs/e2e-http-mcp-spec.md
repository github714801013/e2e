# HTTP MCP 测试服务 P0 规格

状态：需求边界与测试入口已由用户明确确认；规格和后续任务单仅保存在当前仓库；01（动态 Run）、02（HTTP MCP 探索）、03（脚本管理）、04（单 Job 异步执行）、05（并发 Job 与容量）、06（封口、后继 Run 与故障回收）、07（配置启动与完整 P0 本地验收）已实现并本地验证；真实 OA、WSL2 实际部署与反向代理未验证。

本规格基于用户提供的 HTTP MCP 设计文档和两轮已确认的需求澄清。服务端统一控制并发，默认每 Run 上限 4；本次完成完整 P0 实现和本地自动化验证，真实 OA 及 WSL2 实际部署留待环境联调。

## 问题说明

多个已授权 Agent 需要通过同一个 HTTP MCP 服务探索页面、维护测试脚本、提交测试，并在断开请求后继续查询执行结果。同一项目、环境、站点和账号的并发任务需要复用一次登录产生的认证快照，运行中追加作业并按需增加 Worker，避免重复登录和常驻执行进程占用资源。

仅包装现有 STDIO 工具不能满足运行中动态入队和作业级报告的要求。现有上游是否具有相关内部扩展点尚未通过本次源码取证核实；实现前应核验，不能将设计文档的能力表当作代码事实。

## 解决方案

提供单实例 Sidecar 服务，通过 Streamable HTTP 暴露原生探索能力与六个测试管理工具。Gateway 管理认证、客户端归属、脚本、作业记录和报告。RunCoordinator 按 RunKey 协调临时 Runner 子进程，每个 Run 内执行一次认证 Setup、复用认证快照，真正动态追加测试，有待执行任务时按需扩容，封口并完成结果入账后清理资源。

复用原生测试收集、Setup 依赖、Worker、SessionStore、重试、回放缓存和报告能力。核心扩展保持窄边界，围绕动态提交、容量预留、调度唤醒、封口和完整报告，不复制整个 Runner。

12. 作为资源管理员，我希望 Worker 随工作量增长并受上限约束，以便空闲时节约资源、繁忙时有界排队。

14. 作为重连客户端，我希望按权限查询原作业状态，以便 HTTP 连接断开不丢失执行进度。
15. 作为报告使用者，我希望只看到自己获准访问的作业结果、失败概要和安全证据，以便准确定位问题。
16. 作为运维人员，我希望空闲 Run 自动封口并退出，以便浏览器、Worker、Runner 和认证快照被回收。
17. 作为运维人员，我希望区分认证、收集、业务断言、浏览器启动和基础设施故障，以便选择正确恢复动作。
18. 作为维护者，我希望普通静态运行保持兼容，动态新增测试进入完整 Run 报告，以便核心补丁可回归和升级。
19. 作为部署人员，我希望获得明确配置、健康检查、停止方式和联调步骤，以便后续部署至目标 WSL2 环境。

## 实施决定

### 边界与身份

- P0 运行一个 Gateway 实例。RunKey 包含项目、环境、完整规范化 Origin 和账号，站点由服务端 targetId 白名单解析。不同 RunKey 使用不同 Runner 子进程。
- 默认账号语义为 tester，凭据通过环境变量注入；真实账号值、密钥、Cookie 和认证快照不进入模型、日志或公开报告。
- HTTP MCP 会话、探索浏览器会话和 Runner 认证快照是三个不同概念。探索会话不自动继承 Run 登录状态。
- 已认证主体决定客户端身份和工具权限。探索进程与会话绑定主体及独立 MCP 会话 ID；作业和报告访问必须检查主体归属。
- 测试脚本是具有宿主执行权限的受信任代码。P0 仅向受信任编写者授予保存权限，部署文档明确这一信任边界。

### HTTP MCP 与原生代理

- 默认监听 loopback 的 3001 端口，MCP 端点为 `/mcp/e2e`；`/healthz` 为运维健康检查。
- 使用 SDK 实现 Streamable HTTP 协议，不自行实现 JSON-RPC。选用的 SDK 包、版本和 API 必须在实现前核实。
- 每个独立 MCP 客户端会话复用自己的原生 STDIO 子进程，支持 open_session、tools、call、close_session 和指南资源。普通 HTTP 请求不各自重建子进程。
- 使用强随机 Bearer、工具权限表、Host 与 Origin 白名单，反代身份只来自配置的可信代理；跨域默认不放开。
- 请求、脚本大小、队列、同时运行数、时间和输出均有上限。拒绝未经授权的工具、跨主体会话和作业访问、任意命令与站点。
- 探索会话断连后按服务端心跳或 TTL 回收；有执行中的异步 Job 时，单个客户端断线不取消 Job。

### 工具契约

| 工具 | 输入 | 行为与返回 |
| --- | --- | --- |
| list_test_scripts | 可选 prefix、keyword、limit | 在允许的测试目录内发现并列举用例，返回结果受 limit 与服务端上限限制 |
| get_test_script | path | 返回授权目录内合法测试脚本的 UTF-8 源码 |
| save_test_script | path、content、overwrite | 校验路径、大小与写权限，互斥并原子保存，返回保存结果 |
| run_test | targetId、非空 testFiles、可选 idempotencyKey | 验证目标、脚本、队列与主体，异步返回 jobId、runId、status、targetId；不接受 workers |
| get_test_status | jobId | 返回授权作业的状态、统计与时间，无需持有原 HTTP 连接 |
| get_test_report | jobId | 返回该作业结果、分类错误、失败概要和受控证据或预览 |

所有工具采用关闭的输入 Schema，拒绝未知字段、非法类型和超限值。错误通过 MCP 工具约定返回；HTTP 认证和传输错误保留对应协议语义。

### 脚本边界

- 限定在服务端配置的测试根目录，脚本扩展名为 `.e2e.ts`。路径解析同时处理绝对路径、相对路径、父目录穿越、符号链接或 Windows 链接逃逸和现有路径的真实落点。
- 使用同文件系统的临时文件原子替换，保证读者不读到半文件；单文件写互斥，最后一次完整写入生效。覆盖必须有明确 overwrite 意图。
- 用例发现复用原生收集语义。收集会执行脚本顶层代码，应置于受控子进程并受超时和资源约束，不在 HTTP 请求处理进程中任意执行。
- 运行中覆盖不承诺已收集作业重新加载。检测到收集竞争时返回可重试错误，不能交付混合版本脚本。

### Run 与动态执行

- 生命周期为启动、认证、接收、排空、停止、结束；异常进入失败清理。相同 RunKey 的创建、提交、封口和后继 Run 切换串行协调。
- 首次提交创建 Runner 并执行唯一认证 Setup。启动和认证期间到达的作业排队；认证失败使依赖该认证的作业得到明确错误，不继续执行未认证业务。
- 接收中的 Run 支持真正动态追加测试文件，完成正规收集、选择与依赖校验后形成原生执行单元。重复文件的不同提交保留独立执行归属和身份。
- P0 动态作业使用本 Run 已建立的认证快照，不引入任意新增 Setup 依赖。原生依赖与跨作业限制须在适当阶段明确拒绝，不能悄悄漏跑。
- 动态模式按最大 Worker 容量预留调度槽位，仅在有工作时启动所需 Worker，单 Run 同时执行最多 4 个的默认策略由服务端管理。
- 动态模式的空队列不等于最终结束。提交与 seal 使用同一串行化边界，入队唤醒调度。队列为空、所有任务终结且结果全部入账后，才在空闲宽限后封口、清理并结束。
- 默认空闲宽限 2 秒。封口不可逆；DRAINING 或 STOPPING 收到的新任务等旧 Run 停止后进入后继 Run，避免同账号重复登录。
- 不同 Job 的断言失败互相隔离；共享认证失败、Worker 启动失败或 Runner 故障按实际影响范围传播。
- 认证过期不在活动 Run 中覆盖共享快照。真实 OA 是否允许多浏览器上下文并行须后续联调，不从框架能力推定。
- 若原型发现必须降级为批量窗口，需重新提出具体差异并取得决定，不能静默更换已确认目标。

### Job、幂等、报告与 IPC

- 幂等键作用域是调用主体、targetId 和 key。同一请求重试返回同一 Job，避免重复副作用；相同键与不同请求内容应明确拒绝而非悄悄替换已排队内容。
- Job 状态覆盖 queued、collecting、waiting_auth、running 及 passed、failed、timed_out、interrupted、infrastructure_error、rejected。状态和错误分类必须能区分脚本、认证、业务断言、浏览器与进程问题。
- Job 记录先原子持久化为 queued，再发送带版本和关联 ID 的 IPC；只有收到 ACK 才认定 Runner 受理。所有 IPC 消息均做 Schema 校验。
- IPC 不额外开放网络端口；子进程使用固定入口和参数数组，禁止 Shell 拼接或客户端提供启动命令。
- 记录 Job 与原生执行单元和结果 ID 的映射，用其投影作业统计及报告。完整 Run 报告必须包含后续动态入队测试，不能用独立静态运行冒充同一 Run。
- 输出目录和文件名由服务端生成，每 Run 独立。作业文件限制访问权限；证据请求由 jobId 归属解析，拒绝客户端提供任意磁盘路径。
- 报告和安全预览设置输出上限；失败摘要、日志和证据沿用原生脱敏约束。报告结构若改变现有线格式，必须同步契约、有效和无效 fixture 及生产者。
- 确认 Runner 已退出后，将未完成 Job 标为基础设施故障，不自动重试有业务副作用的用例。Gateway 重启时处理已有未终结记录，不能把中断作业误报成功或重复执行。
- 停止服务先停止接收、封口并给予清理宽限，超时后终止遗留子进程和浏览器，返回真实停止结果。

### 默认容量与部署交付

采用需求文档建议的初始值作为服务端默认：请求体 4 MiB，脚本 256 KiB，每 Run Worker 上限 4，同时 Run 上限 2，每 Run 排队 Job 上限 20，空闲宽限 2 秒，Run 时限 30 分钟，Job 时限 15 分钟，启动时限 30 秒，认证时限 2 分钟，停止宽限 20 秒，作业保留期 14 天。实现应使用集中配置和校验，目标 URL 与凭据由部署环境提供。

交付本地启动方式、无真实密钥的配置示例、WSL2 systemd 非 root 服务配置、健康检查、日志、停止、资源限制和真实环境联调说明。当前分支基于 main 的既有提交，不自动同步上游、提交、推送或发布。

## 测试决定

主要验收入口拟采用真实 HTTP MCP 客户端，连接构建后的 Gateway；Gateway 通过实际 Runner 子进程驱动本地确定性测试应用。以外部可观察结果为准，优先复用既有测试工具，不依赖模拟 Scheduler 的私有字段来声称端到端能力已实现。

对入口难以稳定制造的竞态、IPC 断连、计时和清理边界补少量集中测试。测试应证明约束，不镜像实现步骤。先写能失败的行为用例，再实现到通过，并保留普通静态运行的回归。

| 验收项 | 本次本地可验证证据 |
| --- | --- |
| AC-01 HTTP MCP 接入 | 两个客户端完成初始化、工具与资源枚举 |
| AC-02 原生探索与隔离 | 两个会话使用实际原生工具，相互不能读写或关闭 |
| AC-03 登录一次 | 本地应用记录 Setup 登录次数，同 Run 多 Job 只登录一次 |
| AC-04 真正动态追加 | A 尚未结束时提交 B，返回同 runId、不同 jobId，B 在原 Run 执行 |
| AC-05 按需扩容 | 初始单任务仅需一个 Worker，并发新增使执行并行，计数不超过服务端上限 |
| AC-06 有界排队 | 达上限后有序排队，超容量明确拒绝，无超建 Worker |
| AC-07 空闲回收 | 宽限后 Run 结束、子进程和浏览器退出、认证快照删除；边界到达请求归属明确 |
| AC-08 Key 隔离 | 不同项目、环境、Origin 或账号的作业分属独立 Run |
| AC-09 故障隔离 | 一 Job 断言失败时另一 Job 正常完成，认证与进程故障按范围报告 |
| AC-10 断线续行 | 断开提交客户端后 Job 继续，授权重连可查询 |
| AC-11 报告完整 | 重复文件与动态追加均准确进入各自 Job 和完整 Run 报告 |
| AC-12 基线兼容 | 记录核心改动边界，构建并回归静态 Runner、线格式与类型契约；上游更新后的实际重放须如实标注范围 |
| 安全边界 | Bearer/工具权限/Host/Origin/会话归属/Job归属/关闭Schema/路径与链接逃逸/输出上限/秘密脱敏 |
| 幂等与写竞争 | 重试不重复执行、冲突内容拒绝、并发保存保持完整性 |
| 超时与故障回收 | 收集、认证、启动与运行超时，IPC断连、服务重启与退出均无误报成功或自动重放 |

真实 OA 登录和 Token 并发、真实业务数据、实际反代和 WSL2 部署验收明确未包含于本轮通过声明。用户已明确确认上述 HTTP MCP 客户端、构建后的服务和实际 Runner 子进程作为主要验收入口，少量集中测试补充异常与竞态。

## 范围外

文档 P1，包括 OAuth、多副本或分布式调度、账号池、数据库与 Redis、长期 Worker 池、跨 Run 认证持久化、优先级与精准单作业中断。测试服务不提供压测、共享 CDP 浏览器、任意命令、任意路径、任意站点或额外 REST 管理服务；业务数据自动隔离不作保证。
